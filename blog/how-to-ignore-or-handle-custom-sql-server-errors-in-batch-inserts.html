How to Ignore or Handle Custom SQL Server Errors in Batch Inserts

Learn how to suppress or catch user‑defined errors (e.g., 50001) in SQL Server so that batch jobs continue running without interruption.

Why the error stops the Ant job

When a stored procedure raises a user‑defined error with a number greater than 50000, SQL Server expects the message to exist in sys.messages. SSMS will still run the rest of the batch, but the JDBC driver treats the missing message as a fatal exception and aborts the connection. This is why the Ant build fails after the first raised error.

Define the missing message with sp_addmessage

The simplest fix is to add the custom message to the server catalog. Once the message exists, the driver can translate the error and the batch can continue or be caught as expected.

EXEC sp_addmessage @msgnum = 50001,
    @severity = 16,
    @msgtext = N'Custom validation failed – row skipped.';
GO

Catch the error inside the procedure

If you cannot modify the server catalog, wrap the risky statements in a TRY…CATCH block. Inside the CATCH you can log the problem and then use RETURN or continue processing. Using THROW without a message re‑raises the original error, so keep the CATCH logic simple.

Important: SET XACT_ABORT OFF prevents the whole transaction from rolling back when a non‑fatal error occurs.

BEGIN TRY
    EXEC dbo.YourProcedure @param = @value;
END TRY
BEGIN CATCH
    IF ERROR_NUMBER() = 50001
    BEGIN
        PRINT N'Ignored custom error 50001 – continuing.';
        -- optional logging
    END
    ELSE
        THROW; -- re‑raise unexpected errors
END CATCH;

Batch‑level isolation with GO or separate statements

When you run many INSERT statements in a single script, a single RAISERROR can halt the entire batch. Splitting the script with GO creates separate batches, allowing later batches to run even if an earlier one fails. This technique works well for ad‑hoc data loads.

Best practice for automated builds

In CI pipelines (Ant, Maven, etc.) configure the JDBC connection to ignore warnings if you only need to log them. However, for deterministic builds you should either add the custom message to sys.messages or handle it in TRY…CATCH. This guarantees that the build either succeeds or fails for a known reason.

Takeaway: Add missing custom messages or wrap the code in TRY…CATCH so batch jobs don’t abort on user‑defined errors.

People also ask

Does SET ANSI_WARNINGS OFF suppress RAISERROR?

No. It only affects arithmetic overflow, divide‑by‑zero and similar warnings, not user‑defined errors.

Can I suppress the error without changing the stored procedure?

Yes—add the message with sp_addmessage or execute the procedure inside a TRY…CATCH block that swallows error 50001.

What severity should I use for a non‑blocking custom error?

Use severity 10‑16. Severity 20+ terminates the connection, which will always stop the batch.
