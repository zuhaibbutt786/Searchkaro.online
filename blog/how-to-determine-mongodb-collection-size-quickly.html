How to Determine MongoDB Collection Size Quickly

Learn how to interpret MongoDB stats to find the real size of a collection and its indexes.

Decoding the stats() Output

The db.collection.stats() command returns a JSON object that contains several metrics. The most common keys are count, size, storageSize, totalIndexSize, and avgObjSize. Each key represents a different aspect of the collection: count is the number of documents, size is the raw data size, storageSize is the allocated space on disk, and totalIndexSize aggregates all index storage.

Understanding these metrics is essential because they are not always intuitive. For example, size can be smaller than storageSize when the collection is sparse or when the storage engine has allocated more space than the current data requires. avgObjSize gives an average document size, which can help estimate future growth.

When you inspect the output, look for the _id_ index and any custom indexes. The indexSizes object shows how much space each index consumes, which is crucial for performance tuning.

Size vs StorageSize: What They Mean

size reflects the total bytes of all documents in the collection, excluding indexes and padding. storageSize, on the other hand, is the amount of disk space that the collection has actually reserved. In WiredTiger, storageSize is usually a multiple of the page size (often 4KB), so it can be larger than size.

If your storageSize is significantly higher than size, it indicates fragmentation or that the collection has grown and then shrunk. Monitoring this ratio over time can reveal when you need to run a compact operation or rebuild indexes.

Index Sizes and Their Contribution

The indexSizes field lists each index name and its allocated space. The totalIndexSize is the sum of all these values. Indexes can dominate the storage footprint, especially for collections with many compound or hashed indexes.

When planning capacity, add totalIndexSize to storageSize to get the full disk usage. If an index is no longer needed, dropping it can free up a substantial amount of space.

Practical Commands to Measure Size

Use the following shell commands to retrieve the key metrics:

``` // Basic stats var stats = db.myCollection.stats(); printjson(stats);

// Size in megabytes print('Data size (MB):', stats.size / (1024 * 1024));

// Total disk usage (data + indexes) print('Total disk usage (MB):', (stats.storageSize + stats.totalIndexSize) / (1024 * 1024)); ```

These snippets provide quick, human‑readable numbers that can be logged or fed into monitoring dashboards.

Using the Size for Capacity Planning

When forecasting storage needs, multiply the current size by the expected growth rate and add a buffer for indexes and fragmentation. For example, if your collection is 1.5 GB and you anticipate a 20% yearly increase, plan for at least 2 GB next year.

Also consider the impact of write amplification in WiredTiger, which can increase storageSize by up to 10–20% of the data size. Regularly running db.repairDatabase() or compact can mitigate this effect.

Takeaway: Use db.collection.stats() to get accurate data size, but remember storageSize reflects allocated space, and indexes can add a large overhead.

People also ask

How often should I run db.collection.stats() for monitoring?

Run it at least once per day for active collections; for large, write‑heavy collections, a 15‑minute interval is reasonable.

Can I ignore storageSize when calculating disk usage?

No. storageSize plus totalIndexSize gives the true disk footprint; ignoring it underestimates the required storage.
